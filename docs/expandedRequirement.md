# 电子图书馆服务需求说明

> Backend Take-Home：E-Library Service

## 1. 项目背景

电子图书馆服务用于管理数字内容的浏览、借阅与归还。用户可以查询书籍信息、借阅可用的数字内容，并查看自己当前尚未归还的借阅记录。

本任务的重点不是构建完整的商业化图书馆平台，而是通过一个边界清晰、规模适中的后端服务，展示合理的工程设计与实现能力。

## 2. 目标与范围

### 2.1 目标

实现一个可运行、可验证、易维护的后端服务，至少支持以下用户场景：

1. 浏览书籍目录。
2. 查看书籍详情。
3. 借阅书籍。
4. 归还书籍。
5. 查看当前用户已借阅且尚未归还的书籍。

### 2.2 本次任务范围

实现应聚焦于上述核心流程，并覆盖必要的领域模型、API、数据持久化、错误处理和自动化测试。

以下能力不属于必做范围，除非实现它们有助于说明关键设计取舍：

- 用户注册、登录与完整的认证授权系统；
- 图书目录的新增、修改与删除；
- 预约、等待列表与自动分配；
- 续借、逾期、罚款与通知；
- 电子书文件存储、下载与流媒体阅读；
- 面向生产环境的部署、监控与运维平台。

## 3. 功能需求

### 3.1 浏览书籍

服务应提供书籍列表查询能力，至少支持：

- 返回书籍的基本信息；
- 查看书籍总数及当前可借数量（如业务模型包含授权数量）；
- 根据合理的条件进行分页查询；
- 对非法分页参数进行明确校验并返回可识别的错误。

### 3.2 查看书籍详情

服务应支持根据书籍标识查询书籍详情，至少包含：

- 书籍唯一标识；
- 书名；
- 作者或其他必要的书目信息；
- 当前借阅可用性。

当书籍不存在时，应返回明确的资源不存在错误，而不是返回空对象或服务器内部错误。

### 3.3 借阅书籍

服务应支持用户借阅一本书，并满足以下基本规则：

- 借阅请求必须能够识别请求用户和目标书籍；
- 书籍不存在时，借阅失败；
- 书籍没有可用授权时，借阅失败；
- 同一用户不能同时持有同一本书的多个活跃借阅；
- 借阅成功后应创建借阅记录，并减少可用借阅数量（如存在数量限制）；
- 借阅及库存变化应保持一致，不能出现只创建借阅记录但未扣减库存的部分成功状态；
- 多个用户同时竞争有限授权时，服务必须保持库存与借阅记录的一致性。

### 3.4 归还书籍

服务应支持用户归还自己的活跃借阅，并满足以下基本规则：

- 借阅记录不存在时，归还失败；
- 用户不能归还其他用户的借阅；
- 已归还的借阅不能重复释放库存；
- 归还成功后应记录归还时间，并恢复可用借阅数量（如存在数量限制）；
- 借阅状态与库存变化应在同一业务操作中保持一致。

### 3.5 查看当前借阅

服务应支持用户查看自己的活跃借阅记录，至少包含：

- 借阅记录唯一标识；
- 书籍信息；
- 借阅时间；
- 当前借阅状态或归还时间。

默认情况下，该查询只返回请求用户自己的、尚未归还的借阅记录。

## 4. 业务规则与假设

实现可以对需求中未明确说明的部分作出合理假设，但应在 README 或设计文档中记录假设及其影响。建议至少明确以下内容：

- 用户身份如何传递和校验；
- 书籍是否存在有限的数字授权；
- 借阅记录如何表示活跃与已归还状态；
- 并发借阅和归还时，库存一致性如何保证；
- 日期时间的时区与格式；
- 分页参数、排序方式和默认值；
- 不同类型错误对应的 HTTP 状态码与响应格式。

对于未定义行为，应优先选择简单、可解释、可测试的方案，并避免为了覆盖未来场景而过度设计。

## 5. API 要求

API 风格可自行决定，但应满足以下要求：

- 资源命名和 HTTP 方法使用保持一致；
- 请求与响应结构清晰且稳定；
- 对成功和失败场景都有明确的响应语义；
- 输入校验失败、资源不存在、业务冲突和未预期异常应能够区分；
- API 文档或 README 中应说明主要接口、请求参数、响应示例及错误码；
- 如使用身份请求头或其他临时身份方案，应说明其局限性及生产环境替代方案。

## 6. 技术与设计关注点

实现应体现对以下方面的理解和权衡：

- 应用程序架构与模块边界；
- 领域模型与业务不变式；
- API 设计及兼容性；
- 数据访问与事务边界；
- 并发控制和数据一致性；
- 错误处理与可观测性；
- 代码组织、可读性与可测试性；
- 依赖选择及其适用范围；
- 简单实现与扩展能力之间的取舍。

不要求实现所有可能的生产级能力，但应能够解释关键设计决策，包括：为什么这样设计、解决了什么问题、有哪些已知限制，以及在规模扩大时如何演进。

## 7. 测试要求

至少应覆盖：

- 书籍列表和详情查询；
- 正常借阅、归还和当前借阅查询；
- 书籍或借阅记录不存在；
- 重复借阅、无可用授权和越权归还；
- 非法请求参数及必要的输入校验；
- 借阅、归还与库存更新的一致性；
- 有限授权下的并发竞争场景（如适用）。

测试应能够通过项目提供的标准命令执行。测试名称和断言应帮助评审者理解被保护的业务规则，而不仅仅是提高覆盖率数字。

## 8. 交付物

提交内容至少包括：

- 可构建、可运行的源代码；
- README，包含环境要求、启动方式、测试命令和 API 使用说明；
- 数据模型、架构或关键设计取舍的必要说明；
- 自动化测试及其运行方式。

如存在刻意省略的功能、简化的身份模型、已知限制或生产环境改进方向，应在文档中明确说明。

## 9. 范围控制与评审原则

- 请将实现范围控制在合理程度，优先完成核心借阅流程；
- 本题不存在唯一正确答案；
- 评审重点是代码质量、设计清晰度、业务正确性和工程判断；
- 相较于功能数量，更重视可维护的实现和清晰的设计取舍；
- 对于需求中的歧义，应通过文档说明假设，而不是隐式依赖评审者猜测。
